# TickForge — Engineering Handoff for Project 2 (TickForge Distributed)

**Purpose of this document:** give a Claude Code session with no access to the
`tickforge-cpp` repository enough grounded context to understand what was
built, how it works, what was actually measured (versus assumed), and what
a distributed follow-on project should build on top of. Every claim below
either cites a specific file/mechanism that exists in the repository or is
explicitly labeled as reasoning/estimate rather than a measured fact.

---

## 1. Project name and purpose

**TickForge** (repository: `tickforge-cpp`). An educational C++20 simulation
of a concurrent market-data backend, built as a portfolio project to
demonstrate systems-programming fundamentals end to end: ownership and
lifetime, producer/consumer concurrency, TCP networking, and honest,
measured performance evaluation. It is explicitly **not** a production
trading system — no real market connectivity, no trading strategy, no
claims not backed by an actual measurement taken during development.

## 2. Business/use-case description

Simulates the shape of a market-data ingestion-and-query system: multiple
producer threads generate synthetic price updates for four fake instruments
(`AAPL`, `MSFT`, `NVDA`, `AMZN`), a bounded queue hands those updates to a
single processing thread, that thread maintains an in-memory cache of each
instrument's latest known price, and a TCP server lets clients query that
cache with a minimal text protocol:

```
GET AAPL     ->  AAPL 189.42
GET TSLA     ->  NOT_FOUND      (symbol never seen)
GARBAGE      ->  ERROR          (malformed request)
```

No persistence, no authentication, no real feed integration — the "market
data" is entirely self-generated by the process itself.

## 3. Final architecture

```
Producer 1 ──┐
Producer 2 ──┼──> BoundedQueue<MarketDataUpdate> ──> Consumer thread ──> MarketDataEngine
Producer N ──┘         (bounded, blocking)          (single writer)      (shared_mutex cache)
                                                                                │
                                                                    ┌───────────┼───────────┐
                                                                    │           │           │
                                                              Client thread  Client thread  ...
                                                              (TCP handler)  (TCP handler)
                                                                    ▲           ▲
                                                                    │           │
                                                                 Client       Client
                                                              (GET AAPL)   (GET MSFT)
```

| Boundary | Mechanism | Why |
|---|---|---|
| Producers → queue | `BoundedQueue<T>`: 1 mutex + 2 condition variables | Bounded, so a slow consumer applies visible backpressure instead of hiding behind unbounded memory growth |
| Queue → consumer | same queue, blocking `pop()` | One consumer thread is the sole writer to the cache — no write synchronization needed inside the engine |
| Consumer → cache | `std::shared_mutex` inside `MarketDataEngine` | Exactly one writer; added only once concurrent readers (TCP clients) existed |
| Cache → client threads | `shared_mutex` shared (read) lock via `lookup()` | Many concurrent readers, blocking only against the (rare) writer |
| Server → clients | one `std::thread` per accepted TCP connection | Clarity over the throughput of an event loop — a deliberate teaching trade-off |

This is a **single-process, single-machine system**. There is no node
concept, no network boundary between any of these components — everything
above runs inside one OS process's address space.

## 5. Important C++ components and their responsibilities

- **`MarketDataUpdate`** (`include/tickforge/market_data_update.hpp`) — a
  transient input event: `symbol`, `price`, `timestamp`, `sequence_number`.
  Plain struct, no behavior.
- **`Instrument`** (`include/tickforge/instrument.hpp`) — the persisted
  "current state" of one symbol as held in the cache: `symbol`,
  `last_price`, `last_update_time`, `last_sequence_number`. Distinct type
  from `MarketDataUpdate` deliberately — an event and the durable state it
  produces have different lifetimes and roles.
- **`MarketDataEngine`** (`include/tickforge/market_data_engine.hpp`,
  `src/market_data_engine.cpp`) — the thread-safe in-memory cache. Owns a
  `std::unordered_map<std::string, Instrument>` guarded by a
  `std::shared_mutex`. Public surface: `applyUpdate` (insert-or-update,
  rejects stale/duplicate sequence numbers), `lookup` (returns a copy or
  `std::nullopt`), `instrumentCount`.
- **`BoundedQueue<T>`** (`include/tickforge/bounded_queue.hpp`) — a
  generic, header-only, thread-safe blocking queue with a fixed capacity.
  Not market-data-specific; reusable for any `T`. Public surface: `push`,
  `pop`, `shutdown`, `size`, `highWaterMark`.
- **`MarketDataPipeline`** (`include/tickforge/market_data_pipeline.hpp`,
  `src/market_data_pipeline.cpp`) — owns and drives the producer/consumer
  machinery: N producer threads, one consumer thread, a
  `BoundedQueue<MarketDataUpdate>`, and per-run statistics. Public surface:
  `start`, `requestStop`, `stop`, `stats`, `queue`.
- **`TcpServer`** (`include/tickforge/tcp_server.hpp`,
  `src/tcp_server.cpp`) — a localhost-only, thread-per-connection TCP
  server answering the `GET <SYMBOL>` protocol against a
  `const MarketDataEngine&`. Public surface: `start`, `stop`, `port`.
- **`VerboseLog`** (`include/tickforge/verbose_log.hpp`,
  `src/verbose_log.cpp`) — an opt-in, process-wide diagnostic logger, added
  after the four milestones purely for terminal-based observability. Not
  part of the core architecture; every call site pays one relaxed atomic
  load when disabled and nothing else.

## 6. Important classes/functions and why they exist

- **`MarketDataEngine::applyUpdate` returns `bool`**, not `void` — so the
  consumer thread can attribute each processed update to a statistic
  (applied vs. rejected-as-stale) without `MarketDataEngine` itself needing
  to know anything about statistics.
- **`MarketDataEngine::lookup` returns `std::optional<Instrument>` by
  value**, never a reference — this is the single most consequential
  interface decision in the codebase (see §8 and §20).
- **`BoundedQueue::push`/`pop` return `bool`**, `false` meaning "the queue
  was shut down" — this lets callers distinguish "no data because we're
  done" from "no data yet," without throwing.
- **`MarketDataPipeline::requestStop()` vs. `stop()`** — two distinct
  operations, not one: `requestStop()` is a prompt, cross-thread-safe
  "abort now" signal (sets an atomic flag and shuts the queue down
  immediately); `stop()` waits for any still-running producers to finish
  naturally, then tears down. The destructor always calls `requestStop()`
  before `stop()` so destruction is never a surprise long block; a direct
  call to `stop()` alone assumes the caller wants to wait for natural
  completion — see §14 for the real bug this distinction caused.
- **`TcpServer` holds `const MarketDataEngine&`** — enforced at compile
  time, not by convention, that this component can only read market data.
- **`TcpServer`'s fd-closing ownership rule**: `handleClient()` never
  closes its own socket; only `TcpServer::stop()` ever calls `close()` on a
  client fd, after first calling `shutdown(2)` on it and joining its
  handler thread. This specific ordering exists to avoid a close()/fd-reuse
  race between two threads — see §12 and §14.

## 7. Memory-management decisions

- **Rule of Zero everywhere** — no class in this codebase hand-writes a
  destructor, copy constructor, or move constructor for memory it owns.
  `MarketDataEngine`, `Instrument`, `MarketDataUpdate` all rely entirely on
  compiler-generated special member functions, because every member
  (`std::string`, `std::unordered_map`, `std::shared_mutex`, etc.) already
  manages its own resources correctly.
- **Small-string optimization matters here concretely**: the demo/test
  symbols (`"AAPL"`, `"MSFT"`, etc.) are short enough to live inline inside
  `std::string` on libstdc++, so copying or moving an `Instrument`/
  `MarketDataUpdate` does not allocate on the heap for the symbol field.
- **`lookup()` returns a copy, not a reference or pointer** — a small,
  deliberate, SSO-friendly cost traded for interface safety (Milestone 1)
  and later for lock-compatibility (once `shared_mutex` was introduced, a
  lock can never safely hand out a reference to data it's about to
  release).
- **No custom allocators, no memory pools, no manual `new`/`delete`**
  anywhere in the codebase — explicitly out of scope; correctness and
  clarity were prioritized over that class of optimization throughout.

## 8. Ownership/lifetime decisions

- `MarketDataEngine` exclusively owns its `cache_` (`std::unordered_map`).
- `MarketDataPipeline` exclusively owns every thread it creates
  (`producer_threads_`, `consumer_thread_`); its destructor guarantees they
  are all joined before the object is destroyed (a `std::thread` still
  joinable at destruction calls `std::terminate`).
- `TcpServer` exclusively owns its accept thread and every client-handler
  thread, plus every client file descriptor; only `TcpServer::stop()` is
  ever allowed to `close()` a client fd — `handleClient()` never does, to
  avoid a race between a handler thread and `stop()` both touching the
  same fd number.
- `MarketDataPipeline` and `TcpServer` are both explicitly non-copyable
  (deleted copy constructor/assignment) — they own live threads tied to
  their own address, so copying would be meaningless. (Their atomic
  members already disable the compiler-generated versions implicitly; the
  explicit deletion is documentation for a reader.)
- `MarketDataPipeline`'s and `TcpServer`'s thread-ownership model assumes a
  single "owning" thread calls `start()`/`stop()` (typically `main()`).
  The one deliberate exception is `MarketDataPipeline::requestStop()` and
  `TcpServer::stop()` itself, both explicitly documented and designed to be
  safe to call from a different thread than the owner.

## 9. Threading model

Verified directly against the source (no thread pool exists anywhere):

| Thread | Count | Created in | Entry function |
|---|---|---|---|
| Main | 1 | OS-provided | `main()` in `src/main.cpp` |
| Producer | N (configurable; `main.cpp` passes 2) | `MarketDataPipeline::start()` | `MarketDataPipeline::runProducer` |
| Consumer | exactly 1, always | `MarketDataPipeline::start()` | `MarketDataPipeline::runConsumer` |
| TCP accept loop | exactly 1 | `TcpServer::start()` | `TcpServer::acceptLoop` |
| Client handler | 0..N, one per live connection | `TcpServer::acceptLoop()` (i.e., created by the accept thread, not `main`) | `TcpServer::handleClient` |

With the server running and no clients connected: **5 OS threads** (main +
2 producers + 1 consumer + 1 accept loop), plus exactly one more per
currently-connected client. There is **no thread pool**: client-handler
threads are created fresh per accepted connection with no reuse, and
producer/consumer/accept-loop are each a single fixed thread for the
component's lifetime. `MarketDataEngine` and `BoundedQueue` have no thread
of their own — they are passive, synchronized data structures invoked by
whichever thread calls into them.

The main thread only does setup (signal handlers, arg parsing,
construction, calling `start()` on the pipeline and server) and shutdown
orchestration (sleeping in a 100ms poll loop, then calling `stop()` on
both, which blocks it while every other thread is joined). It never
produces, consumes, accepts, or serves anything itself.

## 10. Synchronization mechanisms

- **`BoundedQueue<T>`**: one `std::mutex`, two `std::condition_variable`s
  (`not_full_` for producers, `not_empty_` for the consumer) — separate
  because the two sides wait on different, unrelated conditions.
- **`MarketDataEngine`**: one `std::shared_mutex` — `applyUpdate` takes it
  exclusively (the one writer), `lookup`/`instrumentCount` take it shared
  (many concurrent readers).
- **`TcpServer`**: `std::atomic<int>` for `listen_fd_` (fixed after a real
  ThreadSanitizer-caught data race — it was originally a plain `int`),
  `std::atomic<bool>` for `running_`, and one `std::mutex`
  (`clients_mutex_`) guarding `client_fds_`/`client_threads_`.
- **`MarketDataPipeline`**: `std::atomic<uint64_t>` for `next_sequence_`
  (a single shared sequence-number generator across all producers) and the
  `Stats` counters; `std::atomic<bool>` for `stop_requested_`; a plain
  (non-atomic) `bool stopped_`, correct only because `stop()`/the
  destructor are documented as single-owner-thread operations.
- **`VerboseLog`**: `std::atomic<bool>` for the enabled flag, plus one
  independent `std::mutex` serializing stdout writes — unrelated to any of
  the synchronization above.

## 11. Queue design

`BoundedQueue<T>` (`include/tickforge/bounded_queue.hpp`), a header-only
template (must be, since template definitions need to be visible at every
instantiation point). Internally wraps `std::queue<T>`, which by default is
backed by `std::deque<T>`. Capacity is a `std::size_t` compared against
`queue_.size()` inside a wait predicate — not a preallocated fixed buffer.
`push()` blocks (via `not_full_.wait`) while full; `pop()` blocks (via
`not_empty_.wait`) while empty; both predicates use the predicate-overload
of `wait()`, which handles spurious wakeups automatically by re-checking
the condition. `shutdown()` gives "graceful, drain-then-stop" semantics:
`push()` starts returning `false` immediately, but `pop()` keeps returning
already-queued items until empty, only then also returning `false` —
nothing already enqueued is ever silently dropped. `push`/`pop` always
**move**, never copy, the element (`push(T item)` moves into the internal
deque; `pop(T& out)` move-assigns from the front before destroying it).
`highWaterMark()` (peak occupancy) is a plain `std::size_t`, deliberately
not atomic, since it's only ever touched while `mutex_` is already held —
a concrete example of not reaching for an atomic where a mutex already
covers the state.

## 12. Networking/TCP design

Plain POSIX sockets (`socket`/`bind`/`listen`/`accept`/`recv`/`send`/
`close`), blocking I/O, bound to `127.0.0.1` (`INADDR_LOOPBACK`) only —
never exposed beyond the local machine. Thread-per-connection: one accept
thread hands each new connection to its own handler thread (see §9). TCP
is treated correctly as a byte stream: `handleClient` buffers incoming
bytes per-connection and only processes a complete `\n`-terminated line,
rather than assuming one `recv()` equals one request. Constructor accepts
port `0` to mean "let the OS choose" (resolved via `getsockname()` after
`bind`), used by tests to get a guaranteed-free port with no hardcoding.
Shutdown ordering in `TcpServer::stop()`: `shutdown(2)` every tracked
client fd first (unblocks any thread parked in `recv()`/`send()`), *then*
join every handler thread, *only then* `close()` the fds — this specific
order exists because a data race / fd-reuse hazard would occur if a
handler thread and `stop()` could both `close()` the same fd number
concurrently.

## 13. Error-handling approach

- `std::optional` for the expected "not found" case (`MarketDataEngine::
  lookup`) — not an exception, since a lookup miss is a normal outcome, not
  an exceptional one.
- `std::runtime_error` thrown only for genuine setup failures (`socket`/
  `bind`/`listen` failing in `TcpServer::start()`).
- Malformed or unrecognized client requests produce an `"ERROR"` response,
  never a crash or an exception escaping the handler thread.
- `MSG_NOSIGNAL` used on `send()` (Linux-specific) so a client vanishing
  mid-send returns an error instead of raising `SIGPIPE` and killing the
  whole process over one bad connection.
- `SIGINT`/`SIGTERM` handled via a `std::atomic<bool>` flag set inside the
  signal handler (the only kind of operation guaranteed async-signal-safe
  for this purpose) and polled by the main thread's loop.

## 14. Shutdown approach

Graceful shutdown means **different things in different components**,
and conflating them was a real, found bug:

- **Pipeline** (`MarketDataPipeline`): "graceful" = let already-enqueued
  work drain, then stop — there is a natural end (the queue empties).
  `stop()` joins producers first (safe, since the consumer is concurrently
  draining), then shuts the queue down, then joins the consumer.
  `requestStop()` is a separate, prompt "abort now" signal for a pipeline
  with no natural completion (e.g., configured with `kUnlimitedUpdates` for
  a long-running server). **A real deadlock was found and fixed**: calling
  `stop()` alone on an unlimited-quota pipeline hangs forever, because
  `stop()`'s contract is "wait for producers to finish their quota," and
  an unlimited quota never finishes. The fix was calling `requestStop()`
  before `stop()` (which the destructor already did automatically) — this
  bug was in `main.cpp`'s usage, not in the library, and was caught only by
  manually running the compiled server with a real signal, not by any unit
  test.
- **TCP server** (`TcpServer`): "graceful" = an open client connection has
  no natural end, so instead: forcibly unblock every connection via
  `shutdown(2)`, join every handler thread, only then close their file
  descriptors (see §12).
- **Process** (`main.cpp`): `SIGINT`/`SIGTERM` → atomic flag → main loop
  notices within ~100ms → `server.stop(); pipeline.requestStop();
  pipeline.stop();` → process exits 0.

GoogleTest, fetched via CMake `FetchContent` pinned to tag `v1.18.0` (not a
system package, not vendored, not a moving branch). **24 test cases across

| Suite | File | Count |
|---|---|---|
| `MarketDataEngineTest` | `tests/market_data_engine_test.cpp` | 7 |
| `BoundedQueueTest` | `tests/bounded_queue_test.cpp` | 5 |

| `VerboseLogTest` | `tests/verbose_log_test.cpp` | 2 |

Covers single-threaded correctness (stale-update rejection, FIFO order,
const-correctness), concurrency (blocking/unblocking via real threads and
bounded sleeps, drain-on-shutdown, concurrent clients), the TCP protocol
(via a raw-socket test client deliberately separate from production code),
and lifecycle/shutdown correctness (idempotency, early-abort). One
deliberate omission: no test asserts an exact `highWaterMark()` value under
real concurrent load, since that specific number depends on OS scheduling
and could theoretically flake — the mechanism is instead tested
deterministically, single-threaded, with no timing involved.

Verified beyond GoogleTest: the full suite run repeatedly with no observed
flakiness, and separate ThreadSanitizer builds of both the test binary and
the demo server — which caught a real data race (`listen_fd_` as a plain
`int`, fixed to `std::atomic<int>`) during development. A second real bug
(the shutdown deadlock in §14) was caught only by manually running the
compiled server with a real `SIGINT` — no unit test exercised it, because
the bug was in application-level wiring (`main.cpp`), not in the library
being tested.

## 16. Benchmarking approach

Two small, standalone programs — no benchmarking framework, no external
dependency beyond what the main project already uses:

- **`benchmarks/pipeline_benchmark.cpp`** — varies producer count (1, 2,
  4, 8) at a fixed queue capacity, and queue capacity (8, 64, 1024) at a
  fixed producer count of 4; each configuration runs 200,000 updates per
  producer to natural completion with no artificial pacing delay; reports
  updates/sec via wall-clock timing.
- **`benchmarks/tcp_benchmark.cpp`** — varies client thread count (1, 4,
  16), each sending 2,000 sequential requests over one persistent
  connection; reports req/sec and latency percentiles (avg/p50/p99/max);
  compares an idle cache (no concurrent writer) against a live pipeline (2
  producers) writing concurrently, at the same client counts.

Both link against the same `tickforge_core` library the production
executable uses — there is no separate/duplicated implementation being
benchmarked.

**Measured facts:** throughput drops sharply and reproducibly once
producer count reaches 4 (roughly a 6–10x drop from 2 producers, two
separate runs). At 4 producers, queue capacity 8→1024 changes throughput
under 20% — far less than the ~10x producer-count effect. Every
live-pipeline TCP scenario shows higher average latency than the matching
idle-cache scenario. Median latency is lower at 16 clients than at 1 or 4,
while maximum latency is far higher at 16.

**Hypotheses, explicitly not verified with a profiler:** the throughput
cliff is most plausibly the single-consumer-thread bottleneck (the
queue-capacity result supports this — if capacity were the limit, more
capacity should have helped much more than it did). The machine's
hybrid-core CPU plus WSL2's hypervisor layer are a plausible additional
contributor to the cliff's sharpness and the high tail latencies at 16
clients, but this was never isolated with `perf`, core pinning, or
repeated statistical trials. Lower median / higher max at high concurrency
looks like classic tail-latency behavior (more work keeps the CPU busy
between context switches; a minority of requests wait much longer under
scheduling contention) — a hypothesis about the distribution's shape, not
a proven mechanism.

## 18. Important limitations

- `MarketDataEngine` is not safe against multiple *writers* — it assumes
  exactly one thread ever calls `applyUpdate`. This is correct for the
  current architecture but would need a different design (sharded locks,
  or routing all writers through one queue) if that assumption changed.
- The single consumer thread is a hard, now-*measured* (not just
  predicted) throughput ceiling.
- `double` is used for price — a known, deliberate simplification real
  market-data systems avoid (binary floating point can't exactly represent
  most decimal prices); a fixed-point/integer-cents representation would
  be the honest choice beyond an educational simulation.
- No input validation beyond protocol parsing — acceptable since the only
  untrusted input is a client's raw request line, already validated by the
  parser, and there's no broader attack surface in a localhost-only,
  unauthenticated demo.
- Benchmarks are single/few-trial measurements on one shared, virtualized
  machine — see §17's "what this benchmark cannot tell you" framing.

## 19. Simplifications made for educational purposes

- `double` price instead of fixed-point/integer cents.
- No persistence — all state lives in memory and is lost on process exit.
- No authentication, no TLS, no rate limiting.
- A hardcoded set of 4 demo symbols in `main.cpp`, though the underlying
  `MarketDataEngine`/cache does not itself hardcode a symbol universe — it
  is a general-purpose `unordered_map` keyed by arbitrary strings.
- No real market-data feed integration — updates are entirely synthetic,
  generated by the process itself.
- No custom allocators, memory pools, or lock-free data structures —
  explicitly out of scope throughout.

## 20. Important engineering decisions and their trade-offs

- **One consumer thread.** Trade-off: zero write-synchronization needed
  inside the engine, at the cost of a measured throughput ceiling (§17).
- **Thread-per-connection TCP server**, not event-driven. Trade-off:
  clarity and explicit demonstration of blocking I/O and OS threads, at
  the cost of not scaling to large connection counts (never measured at
  scale in this project).
- **`shared_mutex` added only once concurrent readers existed**, not
  preemptively. Trade-off: simpler earlier milestones, at the cost of
  needing to reason carefully about exactly when the concurrency model
  actually changed.
- **`lookup()` returns a copy, not a reference**, decided in the very
  first milestone. Trade-off: a small, SSO-friendly copy cost, in exchange
  for every later synchronization change (adding `shared_mutex`) requiring
  zero changes to any caller.
- **GoogleTest via `FetchContent`** rather than a hand-rolled assertion
  harness. Trade-off: added first-configure build time (~25s) and an
  external dependency, in exchange for an industry-standard testing
  framework and practice with CMake dependency management.

## 21. Things learned from the project

- Two real bugs were found only through verification *beyond* writing unit
  tests: a ThreadSanitizer-caught data race (`listen_fd_` as a plain `int`
  read/written across threads with no synchronization), and a shutdown
  deadlock caught only by manually running the compiled server with a real
  signal (§14) — no unit test exercised the second one, because the defect
  was in how `main.cpp` used the pipeline's API, not in the library's own
  logic. This is a concrete demonstration that unit tests validate a
  library against its own contract; they cannot catch a caller misusing
  that contract.
- A small, early interface decision (`lookup()` returning by value in the
  very first milestone) turned out to be the single decision that made a
  much later synchronization change (adding `shared_mutex`) free of any
  changes to calling code.
- Measured data both confirmed and sharpened intuition rather than simply
  validating it: the pipeline throughput cliff between 2 and 4 producers
  was much sharper than a "gradual contention degradation" model would
  predict, and the queue-capacity sweep at 4 producers barely moved
  throughput — directly pointing at the single consumer thread, not queue
  size, as the actual bottleneck, something that was only a hypothesis
  before this was measured.

## 22. Things still needing improvement

- No profiling was ever performed (`perf`, flamegraphs) — the throughput-
  cliff explanation in §17 is a well-supported hypothesis, not a proven
  root cause.
- Benchmarks are single/few-trial, one-machine, virtualized-environment
  measurements — no statistical repetition, no variance reporting, no CPU
  pinning, no isolation from other load on the host.
- No persistence or fault tolerance of any kind — a crash loses all state.
- No structured observability beyond the opt-in `VerboseLog` text logger
  and the benchmark programs — no metrics export, no tracing.
- Price representation (`double`) is a known simplification, not fixed.
- The single-consumer-thread and thread-per-connection scaling ceilings
  are measured/predicted but not addressed — they are exactly what a
  distributed or higher-throughput follow-on needs to design around.

## 23. What would need to change for 10x the workload

**This section is reasoning/estimate, not a measurement.** Based on the
measured single-consumer bottleneck (§17), 10x more update throughput
would very likely require either multiple consumer threads or a sharded
cache (partitioning symbols across independent locks), since the current
design's measured ceiling appears well below that — throughput already
dropped roughly 10x between 2 and 4 producers with only one consumer.
10x more concurrent TCP clients would likely strain the thread-per-
connection model (thread creation and context-switch overhead scale with
connection count) before hitting any other limit, which is the case for
event-driven I/O (`epoll`/`io_uring`). At that read volume, the single
`shared_mutex` guarding the whole cache may also become a measurable
contention point, motivating sharding the cache itself rather than a
single lock for the entire map. None of these specific thresholds have
been measured — they are inferences from the bottleneck that *was*
measured.

## 24. What would need to change if distributed across multiple machines

**This section is reasoning/estimate — explicitly the conceptual seed for
Project 2.** TickForge today is a single-process, single-machine system:
the queue, the cache, and every thread live in one address space, and
every synchronization primitive used (`std::mutex`, `std::condition_
variable`, `std::shared_mutex`, `std::atomic`) only coordinates threads
within that one process — none of them has a distributed-systems
analogue. Concretely, distributing this system would require:

- **Replacing or fronting `BoundedQueue<T>`** with something that can
  transport data across a network boundary (a message broker or log,
  conceptually Kafka-like) — the current queue's blocking semantics are
  built on OS thread primitives that simply don't extend across machines.
- **Deciding how `MarketDataEngine`'s single in-memory cache becomes
  multi-node**: either replication (every node holds a full copy, updated
  via some broadcast/consensus mechanism) or partitioning (each node owns
  a subset of symbols and queries get routed to the owner). The current
  codebase has no notion of node identity, replication, or partitioning at
  all — this is a genuinely new design problem, not an extension of
  anything that exists today.
- **Re-examining the "exactly one writer" invariant.** `MarketDataEngine`
  is fast and simple specifically because there is exactly one writer
  thread by construction. Multiple machines each running a
  producer/consumer pipeline implies multiple writers unless one is
  elected the sole writer for a given partition — which introduces leader
  election and failover, neither of which exists anywhere in this
  codebase.
- **Deciding how a client's query reaches the right node.** `TcpServer`
  today answers every query from its own process's cache; a distributed
  version needs either a routing/discovery layer in front of it, or a way
  for any node to answer any query (which reopens the replication question
  above).

## 25. How Project 2 should build upon Project 1

TickForge Distributed should not start from a blank slate conceptually —
it should treat each node as running roughly the *same* internal pipeline
already proven here (producer(s) → bounded queue → single consumer →
synchronized cache → TCP server), and add the distributed layer strictly
**on top of, not instead of**, that structure: an inter-node transport to
replace or feed `BoundedQueue` across machines, a replication or
partitioning strategy for the cache that `MarketDataEngine` implements
locally per node, and a routing/discovery layer in front of each node's
`TcpServer` so a client can reach the right place. The single-node
bottlenecks measured in this project — one consumer thread, thread-per-
connection, one `shared_mutex` per cache — are precisely the list of
things a distributed design should either shard across nodes or explicitly
choose to accept as a known per-node limit, rather than rediscovering them
by trial and error. Every architectural decision in this repository was
made, explained, and where possible measured for exactly this reason: so
the next project can start from verified ground rather than assumption.
