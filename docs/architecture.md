# Architecture — TickForge Distributed

This document explains where this project starts from, where it's headed,
and why. It's a living document: each milestone updates the sections that
change and appends to the decision log at the bottom.

## 1. Where this starts from

Project 1 (`tickforge-cpp`, handoff: [`PROJECT1_HANDOFF.md`](../PROJECT1_HANDOFF.md))
built a single-process, single-machine market-data backend:

```
Producer 1 ──┐
Producer 2 ──┼──> BoundedQueue<MarketDataUpdate> ──> Consumer thread ──> MarketDataEngine
Producer N ──┘         (bounded, blocking)          (single writer)      (shared_mutex cache)
                                                                                │
                                                                    ┌───────────┼───────────┐
                                                                    │           │           │
                                                              Client thread  Client thread  ...
                                                              (TCP handler)  (TCP handler)
```

Everything in that diagram lives inside one OS process. Every synchronization
primitive it uses (`std::mutex`, `std::condition_variable`, `std::shared_mutex`,
`std::atomic`) only coordinates threads sharing one address space - none of
them has a distributed-systems analogue. Two things were *measured*, not
just assumed, and both are direct motivations for this project (Project 1
handoff §17, §23):

- **The single consumer thread is a hard, measured throughput ceiling.**
  Pipeline throughput dropped roughly 10x between 2 and 4 producers, and
  widening the queue's capacity barely moved the number - the bottleneck is
  the one thread doing all the writing, not queue size.
- **The market data is entirely synthetic** - generated by the process
  itself, with no real provider, no network ingestion, and no persistence
  of any kind. A crash loses all state.

Project 1's own handoff (§24-25) names the conceptual gap directly: there is
no node concept, no replication, no partitioning, and no notion of a queue
that survives past one process. This project's job is to fill that gap -
by adding a distributed layer **on top of** the proven single-node pipeline,
not by discarding it.

## 2. Target end-state architecture

```
                                    HOT PATH (low latency)
                                    ══════════════════════
 Real WebSocket
      │  (persistent connection, provider's JSON frames)
      ▼
 C++ ingestion thread
      │  parse -> validate -> normalize
      ▼
 MarketEvent
      │
      ▼
 BoundedQueue<MarketEvent>  ◄── same mechanism as Project 1's queue,
      │                          different job (see §5)
      ▼
 Kafka producer thread
      │  produce(topic="market-events", key=symbol, value=MarketEvent)
      ▼
 ┌─────────────────────────────────────────────────────────┐
 │  Kafka   (partitioned by symbol; the distributed backbone) │
 └─────────────────────────────────────────────────────────┘
      │                                          │
      ▼ consumer group "hot-state"                ▼ consumer group "historical"
 C++ processor                              C++ historical consumer
      │  idempotent upsert                        │  idempotent insert
      ▼                                            ▼
 Redis                                       PostgreSQL
 (current/hot state,                         (durable history,
  one row per symbol)                          append-only)
      │
      ▼
 TCP query service  ◄── client
 (GET AAPL -> reads Redis, not memory)
                                    COLD PATH (durable, can lag)
                                    ═════════════════════════════
```

`MarketDataSource` sits underneath the first two boxes so the same
downstream pipeline can be fed by either a live WebSocket or a recorded
file - see §6.

## 3. How each Project 1 concept evolves

| Project 1 | Project 2 | What changed and why |
|---|---|---|
| N producer threads generate synthetic updates | One ingestion thread reads a real WebSocket | The data source is now external and untrusted (must be parsed/validated); there's exactly one connection, not N independent generators |
| `BoundedQueue<MarketDataUpdate>` between producers and the one consumer | `BoundedQueue<MarketEvent>` between the WS-ingestion thread and the Kafka-producer thread | Same mechanism, different pair of threads, different reason - see §5 |
| One consumer thread writes the whole cache | Kafka partitions + consumer groups let multiple consumer processes share the write load | Directly answers Project 1's *measured* single-consumer ceiling (handoff §17, §23) - ordering is kept per-symbol via partitioning (see §8) so it's not a free lunch |
| `MarketDataEngine`'s in-memory `shared_mutex` cache | Redis | State needs to survive a process crash and be shared across however many query-service processes exist - see §7 |
| No persistence at all | PostgreSQL, fed by a separate historical consumer | A durable record of every event, decoupled from the low-latency hot path - see §4 |
| `TcpServer` reads `const MarketDataEngine&` directly | `TcpServer` reads Redis over the network | Same client-facing protocol shape, different backing store - the query service no longer *is* the state, it *looks up* the state |
| Everything is one process; process death loses everything | Ingestion, Kafka, processor, query service, and historical consumer are independently deployable/restartable | This is the actual meaning of "distributed" here: failure of one part no longer takes down every part (see failure handling, Milestone 5) |

## 4. Hot path vs. cold path

**Hot path** — WebSocket → queue → Kafka → processor → Redis → TCP query.
Optimized for low latency: a client asking "what's AAPL's last price"
should get an answer in low milliseconds. Nothing in this path should ever
block on PostgreSQL.

**Cold path** — Kafka → historical consumer → PostgreSQL. Optimized for
durability and queryability of history, not speed. It reads from the *same*
Kafka topic as the hot path (a second, independent consumer group - see
§8) but on its own schedule. If PostgreSQL is slow or briefly unavailable,
that consumer group falls behind (measurable as consumer lag) while the hot
path keeps serving current state from Redis, unaffected.

This separation is the direct answer to a question Project 1 never had to
ask, because it had no persistence at all: *should durable storage be
allowed to slow down a live query?* The answer here is no, and Kafka's
retention (events aren't deleted the moment they're consumed) is what makes
that possible - the historical consumer can always catch up later.

## 5. Why the bounded queue still exists once Kafka is in the picture

This is worth being precise about, because it's easy to add a queue out of
habit rather than necessity.

librdkafka's `produce()` call is already asynchronous: it hands the message
to the client library's **own** internal bounded queue
(`queue.buffering.max.messages` / `max.kbytes`) and returns immediately; a
background thread inside the library batches messages and ships them to
brokers, invoking a delivery-report callback later. So a second queue that
sits in front of `produce()` and is immediately drained by the same thread
that calls `produce()` would add nothing - it's not decoupling anything
from anything.

The queue earns its place for a different reason: **the WebSocket read loop
and the Kafka producer call must not share a thread.** The read loop has to
keep draining the socket promptly - falling behind risks the provider
buffering data server-side or dropping the connection. The producer call
can stall in ways that have nothing to do with the network read: an initial
broker connection/DNS lookup, a leader-not-available window during a
broker restart, or a full internal librdkafka queue during an outage. If
one thread does both jobs, a Kafka-side hiccup directly and immediately
stalls WebSocket reads - exactly the kind of coupling a bounded queue is
good at removing.

So the design is: one thread owns WS-read → parse → validate → normalize,
and pushes the resulting `MarketEvent` onto `BoundedQueue<MarketEvent>`. A
*separate* thread pops from that queue and calls `produce()`. This is the
same producer/consumer shape as Project 1's queue, reused because it solves
the same category of problem (isolate a latency-sensitive I/O loop from a
slower downstream call) - not merely because Project 1 happened to have a
queue.

**The alternative**, worth naming honestly: skip the app-level queue
entirely, call `produce()` directly from the WS-read thread, and rely
completely on librdkafka's internal buffering and its delivery-report
callback for backpressure and error handling. This is simpler - one fewer
thread, one fewer hand-off - and is a legitimate design many real systems
use. The cost: less controllable, less directly observable backpressure at
the application level (you're reading librdkafka's internal queue stats
instead of a `size()`/`highWaterMark()` you own), and the WS thread's read
loop becomes indirectly coupled to Kafka's internal state regardless -
when that internal queue is full, `produce()` itself blocks or fails
depending on configuration, on the same thread that's supposed to be
draining the socket.

Queue capacity, overflow policy (block vs. reject vs. drop-oldest), and
what "queue full" should actually mean for market data specifically
(silently dropping a trade is not like dropping a metrics sample) are
Milestone 2 decisions, made once the queue has a second thread on the other
end of it to actually decouple from.

## 6. MarketDataSource: live vs. replay

```
         MarketDataSource                 (include/tickforge/market_data_source.hpp)
           /          \
          /            \
   LiveSource       ReplaySource
       |                |
  WebSocket        recorded data
       \                /
        \              /
         normalized
         MarketEvent
```

Interface (already added this milestone, implementations arrive in
Milestone 1):

```cpp
class MarketDataSource {
public:
    virtual ~MarketDataSource() = default;
    virtual void start() = 0;
    virtual void stop() = 0;
    virtual bool next(MarketEvent& out) = 0;
};
```

`next()`'s `bool` return deliberately mirrors `BoundedQueue<T>::push`/`pop`
from Project 1: `false` means "nothing more will ever come" (source
exhausted or `stop()` was called), distinct from "nothing is ready yet."
Same interface convention, applied one layer up the pipeline.

`LiveSource` will own the WebSocket connection, parsing, validation,
normalization, and reconnect logic. `ReplaySource` will read previously
captured, normalized `MarketEvent`s from a file and hand them back through
the identical interface - deterministically, at whatever pace the caller
wants. Everything downstream of `next()` - the bounded queue, the Kafka
producer, all of it - never knows or cares which one it's talking to. This
is what makes deterministic tests, integration tests, and benchmarks
possible without a live provider connection being a hard requirement for
running them (Milestone 6 covers capture/replay in depth).

## 7. Redis vs. process memory vs. PostgreSQL

Three different places "current state" could live, with genuinely
different trade-offs - not a strict speed ranking:

| | Project 1: process memory | Redis | PostgreSQL |
|---|---|---|---|
| Latency | Fastest possible - no network hop, no serialization | A network round-trip plus serialization, slower than local memory by construction | Slower still - durability (WAL fsync) costs real time |
| Durability | None - process exit loses everything | Optional, and typically weaker than a relational DB's guarantees | Strong - the reason it's used for history at all |
| Sharing across processes | Impossible - it's one process's address space | Native - any process that can reach it over the network can read it | Native |
| Consistency | Trivial - one `shared_mutex`, one writer | Depends on the update pattern - needs sequence-number checks to resolve out-of-order writes (§ idempotency, Milestone 3) | Transactional |
| Best fit here | (what Project 1 used) | Hot/current state - the TCP query service's backing store | Historical record - the cold path |

The honest framing: Redis is not "faster than local memory" - it can't be,
since it adds a network hop that local memory doesn't have. What it buys is
something Project 1's architecture structurally couldn't have: state that
outlives any single process and that multiple TCP-query-service processes
can share. That's the actual problem being solved, and it's a genuinely new
one - Project 1 never needed more than one process to be able to see its
cache.

## 8. Kafka: partitioning and ordering

Kafka guarantees ordering **within a partition**, never globally across a
topic. Partitioning the `market-events` topic by `symbol` means every event
for `AAPL` lands in the same partition in the order it was produced, so a
single consumer reading that partition sees `AAPL` events in order. It does
**not** mean events for `AAPL` and `MSFT` have any defined relative order to
each other - they may be interleaved arbitrarily across partitions.

This is also where Project 1's measured bottleneck reappears in a new
shape. A consumer *group* can have at most as many actively-consuming
members as there are partitions - extra members past that point sit idle.
So a single very active symbol (all its events funneling through one
partition) is still capped at the throughput of the one consumer instance
reading that partition, for exactly the same reason Project 1's one
consumer thread capped total throughput. Kafka doesn't remove that
ceiling; it moves it from "the whole system has one consumer" to "each
partition has one active consumer," and gives you a knob (partition count)
to raise it - at the cost of giving up cross-partition ordering, which is
the trade-off being accepted.

## 9. Delivery semantics

This project targets **at-least-once** delivery with **idempotent**
downstream processing - not exactly-once, because the implementation
doesn't genuinely provide it. Concretely: a producer retry after a timed-out
acknowledgment, or a consumer crash after processing but before committing
its offset, can both cause the same event to be delivered more than once.
Redis and PostgreSQL writes are designed (Milestone 3-4) to be safe under
duplicate delivery - via provider/internal sequence numbers - rather than
by trying to prevent duplicates from ever occurring, which distributed
systems generally can't do without much heavier machinery than this project
takes on.

## 10. Time

Two different clocks, used for two different purposes, throughout this
codebase:

- **Wall-clock** (`std::chrono::system_clock`) - represents *when an event
  occurred* (the provider's event timestamp). Can jump forward or backward
  (NTP correction), so it's never used to measure a duration.
- **Monotonic** (`std::chrono::steady_clock`) - represents *elapsed time*
  (ingestion latency, processing duration). Never converted to a calendar
  date; only ever compared against another `steady_clock` reading.

`MarketEvent` (§6, `include/tickforge/market_event.hpp`) already encodes
this split: `event_time` is `system_clock`, `ingest_time` is `steady_clock`.

- **2026-08-29 (Milestone 0)** - Build/run via the `/mnt/d` WSL2 bridge
  rather than moving the repo into WSL2's native filesystem. Keeps a single
  source of truth at the Windows path this session edits directly; accepts
  a small, likely-irrelevant DrvFs I/O overhead on compile in exchange for
  zero workflow friction. Revisit if Kafka/librdkafka build times become
  painful in practice.
- **2026-08-29 (Milestone 1)** - Selected Binance's public spot trade
  stream over Finnhub's real-time equities feed, primarily for 24/7
  availability and a verified, documented forced-disconnect mechanism to
  build and demonstrate reconnect logic against, rather than a hypothetical
  one. Selected Boost.Beast (synchronous API) for the WebSocket/TLS client
  over IXWebSocket/libwebsocketpp - apt-installable (no FetchContent
  source build), and its blocking-call style matches Project 1's
  `TcpServer` design instinct instead of introducing async/coroutines this
  milestone doesn't need. Details and alternatives considered:
  `docs/milestone-1-ingestion.md`. Built, tested (28/28), and run live
  against Binance during this milestone - captured a real 20-second, 329-
  event fixture (`replay/btcusdt_ethusdt_sample.jsonl`) and verified
  deterministic replay reproduces it exactly. One real bug was caught only
  by that manual run, not by any unit test - see
  `docs/milestone-1-ingestion.md` §5.
